1. Setup & first test

Install pytest (preferably inside a virtual environment):

pip install pytest

Create test_sample.py. By default pytest discovers files named test_*.py or *_test.py, classes prefixed Test, and functions prefixed test_.

# test_sample.py
def test_always_passes():
    assert True

def test_arithmetic():
    assert 2 + 2 == 4
    assert 3 * 4 == 12

Run it:

pytest test_sample.py -v
test_sample.py::test_always_passes PASSED
test_sample.py::test_arithmetic PASSED
============================== 2 passed in 0.02s ===============================
💡 Use pytest -v (verbose) / -q (quiet). Running plain pytest discovers everything below the current directory.

2. Assertions & expected exceptions

pytest uses Python's built-in assert but adds rich introspection. Failed assertions show a diff of actual vs. expected values.

def test_failure_demo():
    expected = {"name": "Alice", "age": 30}
    actual = {"name": "Alice", "age": 31}
    assert actual == expected  # pytest shows a helpful diff

Testing exceptions with pytest.raises:

import pytest

def divide(a, b):
    if b == 0:
        raise ValueError("Cannot divide by zero")
    return a / b

def test_divide_by_zero():
    with pytest.raises(ValueError) as excinfo:
        divide(10, 0)
    assert "Cannot divide by zero" in str(excinfo.value)

def test_divide_zero_match():
    with pytest.raises(ValueError, match="divide by zero"):  # regex
        divide(1, 0)

Exception groups (Python 3.11+)

import pytest

def raises_group():
    raise ExceptionGroup("many errors", [ValueError("a"), TypeError("b")])

def test_group():
    with pytest.raises(ExceptionGroup) as exc:
        raises_group()
    assert len(exc.value.exceptions) == 2

3. Assertion rewriting — the magic explained advanced

pytest rewrites the AST of every test module before execution. That's why:

  • You write plain assert (no self.assertEqual).
  • Failed assertions show the values of intermediate expressions.
  • Asserts work even when Python is run with -O (which normally strips them).
def test_rewrite_demo():
    a, b = 1, 2
    assert a + b == 4
    # E   assert (1 + 2) == 4
    # E    +  where 1 = a
    # E    +  and   2 = b

Disable with --assert=plain (rarely useful) or per-module with PYTEST_DONT_REWRITE.

📌 Assertion rewriting does not work inside exec(), eval(), or list/generator comprehensions on some Python versions. Keep assertions simple.

4. Fixtures — the heart of pytest

Fixtures provide a baseline for tests: data, connections, temp files, or anything reusable. Defined with @pytest.fixture, injected by name.

import pytest

@pytest.fixture
def sample_list():
    return [1, 2, 3, 4, 5]

def test_sum(sample_list):
    assert sum(sample_list) == 15

def test_length(sample_list):
    assert len(sample_list) == 5

Fixture scopes

Default scope is function. Other scopes: class, module, package, session.

@pytest.fixture(scope="module")
def expensive_resource():
    print("\n[setup]")
    resource = {"data": [1, 2, 3]}
    yield resource
    print("\n[teardown]")

def test_one(expensive_resource):
    assert expensive_resource["data"][0] == 1

def test_two(expensive_resource):
    assert len(expensive_resource["data"]) == 3

Fixtures requesting other fixtures

@pytest.fixture
def base_url():
    return "https://api.example.com"

@pytest.fixture
def api_client(base_url):
    return {"base": base_url, "timeout": 5}

def test_client(api_client):
    assert api_client["base"].startswith("https")
🔁 Autouse: @pytest.fixture(autouse=True) applies a fixture to every test in scope without explicit injection. Use --setup-show to see the order.

5. Parametrization — one test, many cases

import pytest

def is_even(n):
    return n % 2 == 0

@pytest.mark.parametrize("number, expected", [
    (2, True), (3, False), (0, True), (-4, True), (7, False),
])
def test_is_even(number, expected):
    assert is_even(number) == expected

Stack decorators for combinations (4 runs here):

@pytest.mark.parametrize("x", [0, 1])
@pytest.mark.parametrize("y", [2, 3])
def test_combinations(x, y):
    assert x + y > 0

Use pytest.param for custom IDs, marks, or skip:

@pytest.mark.parametrize("value, expected", [
    pytest.param(2, 4, id="positive"),
    pytest.param(-2, 4, id="negative"),
    pytest.param(0, 0, id="zero"),
    pytest.param(5, 25, id="skip-me", marks=pytest.mark.skip(reason="example")),
])
def test_square(value, expected):
    assert value * value == expected

Readable IDs via ids

@pytest.fixture(params=[0, 1], ids=["zero", "one"])
def fixture_num(request):
    return request.param

# or on parametrize directly
@pytest.mark.parametrize("n", [0, 1], ids=["zero", "one"])
def test_ids(n):
    assert n in (0, 1)

Dynamic parametrization via pytest_generate_tests

# conftest.py
def pytest_generate_tests(metafunc):
    if "value" in metafunc.fixturenames:
        metafunc.parametrize("value", [10, 20, 30])

6. Marks: skip, xfail, and custom

  • @pytest.mark.skip — always skip.
  • @pytest.mark.skipif — skip conditionally.
  • @pytest.mark.xfail — expected to fail.
  • @pytest.mark.<name> — custom marks selectable with -m.
import sys
import pytest

@pytest.mark.skip(reason="feature not implemented yet")
def test_future(): ...

@pytest.mark.skipif(sys.version_info < (3, 10), reason="3.10+")
def test_new_syntax():
    assert (x := 5) == 5

@pytest.mark.xfail(reason="known issue #123")
def test_flaky():
    assert 1 == 2

@pytest.mark.slow
def test_slow_thing():
    import time; time.sleep(2)

Run only marked: pytest -m slow. Exclude: pytest -m "not slow". Register markers to silence warnings:

[pytest]
markers =
    slow: marks tests as slow
    integration: integration tests

@pytest.mark.usefixtures

Apply a fixture without receiving its return value (useful for setup-only fixtures):

@pytest.fixture
def reset_db():
    db.clear()
    yield
    db.clear()

@pytest.mark.usefixtures("reset_db")
def test_something():
    # reset_db runs but we don't need its value
    assert True

7. Monkeypatch & mocking

monkeypatch temporarily modifies attributes, dicts, env vars, or sys.path, then restores automatically.

import os

def get_api_key():
    return os.environ.get("API_KEY", "default")

def test_api_key(monkeypatch):
    monkeypatch.setenv("API_KEY", "secret123")
    assert get_api_key() == "secret123"

def test_chdir(monkeypatch, tmp_path):
    monkeypatch.chdir(tmp_path)
    assert tmp_path == __import__("pathlib").Path.cwd()

def test_syspath(monkeypatch, tmp_path):
    monkeypatch.syspath_prepend(str(tmp_path))
    assert str(tmp_path) in __import__("sys").path

Replace attributes with monkeypatch.setattr:

import requests

def fetch_data(url):
    return requests.get(url).json()

def test_fetch_data(monkeypatch):
    class MockResponse:
        @staticmethod
        def json(): return {"mocked": True}
    def mock_get(*a, **k): return MockResponse()
    monkeypatch.setattr(requests, "get", mock_get)
    assert fetch_data("https://fake.com") == {"mocked": True}

For deeper control use unittest.mock (built-in) or the pytest-mock plugin:

from unittest.mock import patch

def test_with_patch():
    with patch("requests.get") as mock_get:
        mock_get.return_value.json.return_value = {"ok": True}
        assert fetch_data("http://test") == {"ok": True}
        mock_get.assert_called_once_with("http://test")

8. Built-in fixtures: tmp_path, capsys, caplog

tmp_path — temporary directories

def test_write_file(tmp_path):
    file = tmp_path / "data.txt"
    file.write_text("hello")
    assert file.read_text() == "hello"

def test_multiple_files(tmp_path):
    (tmp_path / "a.txt").write_text("A")
    (tmp_path / "b.txt").write_text("B")
    assert sorted(p.name for p in tmp_path.iterdir()) == ["a.txt", "b.txt"]

tmp_path_factory for session-scoped dirs. Legacy tmpdir (py.path) still exists — prefer tmp_path.

capsys — capture stdout / stderr

import sys

def test_print_output(capsys):
    print("hello world")
    print("this is stderr", file=sys.stderr)
    captured = capsys.readouterr()
    assert captured.out == "hello world\n"
    assert "stderr" in captured.err

Use capfd for file-descriptor-level output (C extensions).

caplog — capture logging

import logging

def test_logging(caplog):
    logger = logging.getLogger("myapp")
    with caplog.at_level(logging.WARNING):
        logger.warning("something bad")
        logger.info("ignored")
    assert "something bad" in caplog.text
    assert caplog.records[0].levelname == "WARNING"
    assert caplog.records[0].name == "myapp"

9. pytest.approx & warnings

Floating-point comparisons with tolerance:

import pytest

def test_float_equality():
    assert 0.1 + 0.2 == pytest.approx(0.3)
    assert 0.1 + 0.2 == pytest.approx(0.3, abs=1e-9)
    assert [0.1 + 0.2, 1.0] == pytest.approx([0.3, 1.0])
    assert {"x": 0.1 + 0.2} == pytest.approx({"x": 0.3})
    assert float("nan") == pytest.approx(float("nan"), nan_ok=True)

Testing warnings:

import warnings
import pytest

def old_function():
    warnings.warn("this is deprecated", DeprecationWarning)

def test_warning():
    with pytest.warns(DeprecationWarning, match="deprecated"):
        old_function()

def test_deprecated():
    with pytest.deprecated_call():
        old_function()

To ensure no warning is raised:

def test_no_warning():
    with warnings.catch_warnings():
        warnings.simplefilter("error")
        normal_function()

12. Import modes & the __init__.py question advanced

pytest has three import modes via --import-mode:

  • prepend (default) — inserts the test's directory at the front of sys.path. Simplest, but can shadow same-named modules across directories.
  • append — inserts at the end. Only relevant if you need a specific resolution order.
  • importlib — imports test modules by file path without touching sys.path. Requires __init__.py in test dirs to avoid module-name clashes.

Do you need __init__.py in tests?

  • Traditional project (tests import from an installed package): no.
  • Same test module name in two folders: yes, or use --import-mode=importlib.
  • Ship tests as a package: yes.
📌 Default behaviour works for 90% of projects. Only reach for --import-mode=importlib when you hit "import file mismatch" errors.

13. conftest.py hierarchy & fixture override rules advanced

conftest.py files are auto-discovered per directory. Fixtures defined there are available to all tests below that directory — no import needed.

my_project/
├── conftest.py # session-wide fixtures
├── tests/
│ ├── conftest.py # applies to tests/ and below
│ ├── test_api.py
│ └── integration/
│ ├── conftest.py # only this subfolder
│ └── test_db.py

Override rules: a fixture with the same name in a deeper conftest.py overrides the outer one. Tests can also override per-module by defining a local fixture.

# tests/conftest.py
import pytest

@pytest.fixture
def api_client():
    return {"env": "test"}

@pytest.fixture
def db():
    yield "real-db"
# tests/integration/conftest.py — overrides for this folder
import pytest

@pytest.fixture
def api_client():
    return {"env": "integration"}

@pytest.fixture
def db():
    yield "fake-db"
# tests/test_api.py
def test_env(api_client):
    assert api_client["env"] == "test"
# tests/integration/test_db.py
def test_env(api_client):
    assert api_client["env"] == "integration"
⚠️ conftest.py is not a plugin — it can't be imported by arbitrary modules and isn't distributed with your package. For reusable fixtures, ship a plugin.

14. Advanced fixtures & the request object

Fixtures can accept the special request fixture, exposing request.param, request.cls, request.node, request.config, and request.addfinalizer.

Parametrizing fixtures

@pytest.fixture(params=[1, 2, 3])
def number(request):
    return request.param

def test_number_positive(number):
    assert number > 0   # runs 3 times

Indirect parametrization

@pytest.fixture
def user(request):
    return {"id": request.param, "name": f"User{request.param}"}

@pytest.mark.parametrize("user", [1, 2], indirect=True)
def test_user_id(user):
    assert user["id"] in [1, 2]

Factory pattern (return a function from a fixture)

@pytest.fixture
def make_user():
    def _make_user(name, age):
        return {"name": name, "age": age}
    return _make_user

def test_multiple_users(make_user):
    alice = make_user("Alice", 30)
    bob = make_user("Bob", 25)
    assert alice["name"] != bob["name"]

Finalization with addfinalizer

@pytest.fixture
def resource(request):
    r = {"status": "open"}
    def teardown():
        r["status"] = "closed"
    request.addfinalizer(teardown)
    return r

def test_resource(resource):
    assert resource["status"] == "open"
📌 yield vs. addfinalizer: yield is cleaner for simple teardown. Use addfinalizer when you need conditional or multiple cleanup hooks.

15. Class-based tests

Group related tests in a class. setup_method/teardown_method run before/after each method; class-level variants are setup_class/teardown_class.

import pytest

class Calculator:
    def add(self, a, b): return a + b
    def divide(self, a, b):
        if b == 0: raise ValueError("division by zero")
        return a / b

class TestCalculator:
    def setup_method(self):
        self.calc = Calculator()

    def test_add(self):
        assert self.calc.add(1, 2) == 3

    def test_divide(self):
        assert self.calc.divide(10, 2) == 5.0

    def test_divide_zero(self):
        with pytest.raises(ValueError):
            self.calc.divide(1, 0)
💡 Prefer fixtures over setup_method — more composable. Class-based is useful for porting from unittest.

pytest runs unittest.TestCase subclasses too, so migration is gradual:

import unittest

class TestLegacy(unittest.TestCase):
    def test_equal(self):
        self.assertEqual(2 + 2, 4)

19. Running subsets — node ID syntax new

Every test has a node ID. You can address any subset precisely:

# single function
pytest tests/test_calc.py::test_add

# class + method
pytest tests/test_calc.py::TestCalc::test_add

# specific parametrized case
pytest tests/test_calc.py::test_add[1-2]

# keyword expressions
pytest -k "add and not slow"
pytest -k "TestCalc and divide"

# by marker
pytest -m "integration and not slow"

# last failed / failed first
pytest --lf
pytest --ff

# collect only (don't run)
pytest --collect-only
pytest --co -q     # quiet collection

20. Runtime helpers: skip, fail, xfail

import pytest

def test_conditional_skip():
    if not has_network():
        pytest.skip("no network available")
    assert True

def test_expected_failure():
    if not feature_flag_enabled():
        pytest.xfail("feature flag off")

def test_explicit_fail():
    if unexpected_condition():
        pytest.fail("something went wrong", pytrace=False)

# skip a whole module at import time
pytestmark = pytest.mark.skipif(no_gpu(), reason="requires GPU")

# fail based on environment
if not os.environ.get("RUN_SLOW"):
    pytestmark = pytest.mark.skip(reason="RUN_SLOW not set")

Use pytest.importorskip for optional dependencies:

def test_numpy():
    np = pytest.importorskip("numpy")
    assert np.array([1, 2]).sum() == 3

22. Hooks & writing your own plugin advanced

Hooks go in conftest.py or your own plugin module. The most-used ones:

# conftest.py
import pytest

def pytest_addoption(parser):
    parser.addoption("--env", action="store", default="dev",
                     help="target environment")

@pytest.fixture
def env(request):
    return request.config.getoption("--env")

def pytest_configure(config):
    config.addinivalue_line("markers", "smoke: quick smoke tests")

def pytest_collection_modifyitems(config, items):
    for item in items:
        if "integration" in item.nodeid:
            item.add_marker(pytest.mark.integration)

def pytest_report_teststatus(report):
    # custom status character
    if report.when == "call" and report.passed:
        return report.outcome, "P", "PASSED"

def pytest_sessionfinish(session, exitstatus):
    print(f"\nsession finished with status {exitstatus}")

CLI usage:

pytest --env=prod

Writing a distributable plugin

# myplugin.py
def pytest_configure(config):
    config.addinivalue_line("markers", "custom: my marker")
# pyproject.toml
[project.entry-points.pytest11]
myplugin = "myplugin"

After pip install -e ., your plugin loads automatically. Verify with pytest --trace-config.

23. Property-based testing with Hypothesis advanced

pip install hypothesis
from hypothesis import given, strategies as st

@given(st.integers(), st.integers())
def test_add_commutative(a, b):
    assert a + b == b + a

@given(st.lists(st.integers()))
def test_sorted_is_ordered(xs):
    assert all(sorted(xs)[i] <= sorted(xs)[i+1] for i in range(len(xs)-1))

Hypothesis generates hundreds of inputs (including edge cases) and shrinks failures to the smallest reproducer. Combine with pytest's normal fixtures.

24. Sub-tests — multiple failures per test new

Traditionally, when the first assertion in a loop fails, the rest never run. Sub-tests solve this — each iteration is reported separately, and all failures are shown at once.

Option A: Native (pytest 8.4+)

import pytest

def test_files_have_docstrings(subtests):
    for path in Path.cwd().glob("*.py"):
        with subtests.test(path=str(path)):
            assert path.read_text().startswith('"""')

Option B: pytest-subtests plugin (backwards compatible)

pip install pytest-subtests
def test_many_assertions(subtests):
    for i in range(5):
        with subtests.test(msg="checking", i=i):
            assert i % 2 == 0  # shows ALL failures at once
💡 Use sub-tests when iterating over files, records, or parameters that are not known at collection time. For known values, prefer @pytest.mark.parametrize.

26. Customizing fixtures with CLI args & markers advanced

Real-world pattern: same test suite, different backends. Let users switch via CLI flag or marker.

Fixture reacting to a CLI option

# conftest.py
import pytest

def pytest_addoption(parser):
    parser.addoption("--use-db", action="store_true", default=False,
                     help="use the real database instead of the fake one")

@pytest.fixture

Fixture reacting to a marker

@pytest.fixture

    # marker-based fixture switching
    if request.node.get_closest_marker("slow"):
        return RealAPIClient(timeout=30)
    return MockAPIClient()

@pytest.mark.slow
def test_full_network_roundtrip(api_client):
    assert api_client.is_real

Fixture reacting to request.param with conditional setup

@pytest.fixture(params=["sqlite", "postgres"])
def backend(request):
    if request.param == "sqlite":
        db = connect_sqlite(":memory:")
    else:
        db = connect_postgres(os.environ["PG_URL"])
    yield db
    db.close()
💡 This pattern lets you keep one test suite that runs against multiple environments without duplicating tests.

27. Flaky test mitigation new

Flaky tests are the #1 cause of CI distrust. Here's how to hunt and tame them.

Detect flakiness

pip install pytest-randomly pytest-rerunfailures
  • pytest-randomly — shuffles test order every run. If tests fail intermittently, you have hidden state.
  • pytest --lf — reruns only previously failed tests to confirm.
  • pytest -p no:cacheprovider --lf — clean rerun.

Rerun flaky tests (temporary mitigation)

pip install pytest-rerunfailures
pytest --reruns 3 --reruns-delay 1

Or per-test:

@pytest.mark.flaky(reruns=3, reruns_delay=2)
def test_unreliable_external_api():
    assert call_flaky_endpoint() == "ok"
⚠️ Reruns hide flakiness — always log and investigate. Prefer fixing the root cause (shared state, time, network, order-dependence).

Common flakiness causes

SymptomRoot causeFix
Passes alone, fails in suiteTest interdependenceIsolate state; use pytest-randomly
Random failures on timeTime-dependent codefreezegun / pytest-freezegun
Fails under parallel runShared ports, files, DBUnique temp dirs (tmp_path), random ports, per-worker DB
Race conditionsAsync timingUse events, not sleep; use pytest-timeout
Network timeoutsExternal dependencyMock or --reruns (last resort)

pytest-xdist caveats

  • Tests run in separate processes — no shared in-memory state.
  • Session-scoped fixtures are per-worker, not global.
  • Ports, files, and databases must be unique per worker (request.config.workerinput exposes the worker id).
  • Output ordering is non-deterministic — use -p no:randomly together with -n carefully.
@pytest.fixture(scope="session")
def unique_db(request):
    worker = getattr(request.config, "workerinput", {}).get("workerid", "master")
    return f"test_db_{worker}"

Test naming conventions

  • File: test_<module>.py
  • Class: Test<Feature> (no __init__)
  • Function: test_<behavior>_<condition>_<expected>
  • Prefer descriptive over clever: test_login_with_wrong_password_returns_401

Arrange-Act-Assert

30. Anti-patterns & pitfalls

❌ Test interdependence

# BAD — test_b assumes test_a ran
counter = 0
def test_a(): global counter; counter += 1
def test_b(): assert counter == 1

# GOOD — each test is self-contained
def increment(n): return n + 1

def test_a(): assert increment(0) == 1
def test_b(): assert increment(0) == 1

❌ Module-scoped mutable state leaking

# BAD — mutations leak across tests
@pytest.fixture(scope="module")
def shared_list():
    return []

# GOOD — copy, or use function scope
@pytest.fixture(scope="module")
def shared_list():
    data = []
    yield data
    data.clear()

❌ Over-mocking

If you mock everything, you're testing your mocks. Mock only at boundaries (network, DB, filesystem). Prefer fakes for simple cases.

❌ Slow fixtures without broader scope

A 500ms DB connection recreated per test adds up fast. Use scope="module" or "session" if tests don't mutate shared state.

❌ Many unrelated asserts in one test

The first failure hides the rest. Prefer one logical assertion per test, or use parametrize / subtests.

❌ Relying on print()

Use capsys / caplog so tests can assert on output.

❌ Relying on test execution order

Tests must be independent. Install pytest-randomly to catch order-dependence bugs early.

❌ Hardcoded paths and ports

Use tmp_path and ephemeral ports (socket.bind(("", 0))) to avoid clashes in parallel runs.

❌ Testing private functions directly

Prefer testing through the public API. If you must test privates, a leading underscore still means "implementation detail — free to change".

31. Common errors → fixes new

ModuleNotFoundError: No module named 'myapp'

Test file can't find your package. Fix with one of:

  • pip install -e . (recommended)
  • Add pythonpath = ["src"] to pyproject.toml under [tool.pytest.ini_options]
  • Add a conftest.py at the repo root (pytest inserts rootdir on sys.path)
import file mismatch: imported module 'test_x' has this __file__ attribute...

Two test modules share a name across folders. Fix:

  • Add __init__.py to test folders, or
  • Run pytest --import-mode=importlib
PytestUnknownMarkWarning: Unknown pytest.mark.slow

Register custom marks in config:

[pytest]
markers =
    slow: marks tests as slow

Or run with --strict-markers to make it an error.

fixture 'xyz' not found

Check: spelling, that the fixture is defined in this file / a conftest.py above, and that @pytest.fixture decorator is present.

ScopeMismatch: You tried to access a 'function' scoped fixture from a 'module' scoped fixture

A wider-scope fixture requested a narrower one. Fix: broaden the inner fixture's scope, or restructure so the narrower fixture requests the wider one.

RuntimeError: no running event loop

Async test without @pytest.mark.asyncio (or asyncio_mode = "auto"). See §16.

DeprecationWarning: pytest.warns(None) is deprecated

Use warnings.catch_warnings() with warnings.simplefilter("error") instead. See §9.

Tests pass individually but fail together

State leaks between tests. Run pytest -p no:randomly --lf, or install pytest-randomly to catch ordering issues. Look for module-level globals, shared fixtures with scope="module", or mutated default arguments.

Fixture finalizer not called / teardown not running

Check that the fixture uses yield (or request.addfinalizer) and that exceptions inside the test don't prevent teardown (pytest always runs finalizers). If setup fails before yield, teardown won't run — the setup itself is the test's failure.

WarningSummary: X warnings

Configure filters in pyproject.toml:

[tool.pytest.ini_options]
filterwarnings = [
    "error",
    "ignore::DeprecationWarning:my_legacy_module",
]

🎤 pytest Interview Questions 60+ Q&A

Sixty-plus interview questions covering pytest from junior to senior level. Click any question to reveal the answer.

Easy — expected of any pytest user Intermediate — mid-level engineer Advanced — senior / test-infra roles

Fundamentals

1 What is pytest and why use it over unittest?

pytest is a Python testing framework. Advantages over unittest:

  • Plain assert with rich rewriting instead of self.assertEqual methods
  • Fixtures instead of setUp/tearDown — more composable and granular
  • Parametrization built in
  • Massive plugin ecosystem
  • Auto-discovery — no boilerplate
  • Runs unittest.TestCase classes too, so migration is gradual
2 How does pytest discover tests?

By default:

  • Files named test_*.py or *_test.py
  • Classes prefixed Test (no __init__)
  • Functions prefixed test_
  • Starts from the current directory or testpaths in config

Configurable via python_files, python_classes, python_functions.

3 What is assertion rewriting in pytest?

Before running tests, pytest parses and rewrites the AST of test modules, replacing each assert with a call that captures intermediate values. This produces readable failures like assert (1 + 2) == 4 and works even under python -O.

4 What is the difference between pytest.raises and try/except?

pytest.raises fails the test if the exception is not raised, and can assert on the message via match. try/except silently passes if no exception occurs, which is usually a bug.

with pytest.raises(ValueError, match="bad"):
    divide(1, 0)
5 How do you run a single test? 
pytest tests/test_calc.py::test_add
pytest tests/test_calc.py::TestCalc::test_add
pytest tests/test_calc.py::test_add[1-2]

Fixtures

6 What is a fixture in pytest?

A fixture is a function decorated with @pytest.fixture that provides setup data or resources to tests. Tests request fixtures by name as arguments. Fixtures can return values or use yield for setup/teardown.

7 What are the fixture scopes and when do you use each?
  • function (default) — fresh per test. Safe but slow if setup is heavy.
  • class — once per test class.
  • module — once per test file.
  • package — once per package.
  • session — once per test session. Use for expensive resources (DB engine, HTTP client) when tests don't mutate them.
8 How do fixtures interact with each other?

Fixtures can request other fixtures by name as arguments. pytest resolves the dependency graph and caches results according to scope. This enables composition.

@pytest.fixture
def db_conn(db_url):
    return connect(db_url)
9 What is the difference between yield and request.addfinalizer in fixtures?

Both register teardown. yield is the modern, cleaner form for a single teardown. Use request.addfinalizer when you need to register multiple conditional cleanup callbacks.

10 How can a fixture know which test is using it?

Request the built-in request fixture. Then access request.node (the test item), request.function, request.cls, request.config, or request.node.get_closest_marker("...") to branch behaviour by marker.

11 What is autouse=True and when should you use it?

It makes a fixture apply to every test in scope without being explicitly requested. Use sparingly — for cross-cutting concerns like logging or environment setup. Overuse hides dependencies.

12 What is a fixture factory pattern?

A fixture that returns a function so tests can create multiple objects with different args:

@pytest.fixture
def make_user():
    def _make(name, age):
        return User(name, age)
    return _make
13 How do you make a fixture return different values for different tests?

Use @pytest.fixture(params=[...]) and read request.param. Each param value triggers a separate test run. Use ids= for readable names.

14 Explain conftest.py hierarchy and fixture override rules.

Each directory can have a conftest.py loaded for that directory and its children. Fixtures defined in a conftest.py are visible to all tests below it. If a child conftest.py defines a fixture with the same name, it overrides the parent for tests in that subtree. Tests can also override per-module by defining a local fixture.

15 Why does a session-scoped fixture fail when it requests a function-scoped fixture?

Because the wider scope would need to cache a value that changes per test. pytest raises ScopeMismatch. Fix: broaden the inner fixture's scope, or restructure so the function-scoped fixture requests the session-scoped one (never the reverse).

Parametrization & Marks

16 What does @pytest.mark.parametrize do?

It runs the same test function with multiple sets of arguments, generating one test case per parameter set. Failures are reported individually.

17 How do you skip or xfail a test?

Skip: @pytest.mark.skip or @pytest.mark.skipif(cond, reason=...). Expected failure: @pytest.mark.xfail. Runtime: pytest.skip(), pytest.xfail(), pytest.fail().

18 What is the difference between skip, xfail, and fail?
  • skip — not run, not a failure.
  • xfail — run; if it fails, that's expected (marked xfail); if it passes, marked xpass. xfail_strict = true makes xpass an error.
  • fail — force a failure with a message.
19 How do you run only tests with a specific marker? 
pytest -m slow
pytest -m "integration and not slow"

Register markers in pytest.ini to avoid warnings:

[pytest]
markers =
    slow: marks tests as slow
20 Can you stack multiple parametrize decorators?

Yes — the result is the Cartesian product of all parameter sets. Order matters for readability of node IDs.

21 How do you use pytest.param to attach marks to a specific parametrize case? 
@pytest.mark.parametrize("x, y", [
    pytest.param(1, 1, id="one-one"),
    pytest.param(2, 2, marks=pytest.mark.skip(reason="todo")),
])
def test_pair(x, y):
    assert x == y
22 What is indirect=True in parametrize?

It sends the parametrized values through a fixture instead of the test directly. Useful when the fixture must transform the parameter (e.g., construct an object).

@pytest.mark.parametrize("user", [1, 2], indirect=True)
def test_user(user):
    assert user.id in (1, 2)

Built-in fixtures

23 What are tmp_path and tmp_path_factory?

tmp_path is a function-scoped fixture returning a unique pathlib.Path per test, cleaned up automatically. tmp_path_factory produces temp directories at session or module scope.

24 How do you capture stdout in a test?

Request the capsys fixture (or capfd for FD-level output) and call capsys.readouterr() to get a namedtuple with .out and .err.

25 How do you capture logs in a test?

Use the caplog fixture:

def test_log(caplog):
    with caplog.at_level(logging.WARNING):
        logger.warning("boom")
    assert "boom" in caplog.text
26 How do you temporarily change an environment variable?

Use monkeypatch.setenv("KEY", "value"). It's restored automatically after the test.

27 How do you capture warnings?

Use pytest.warns(Category, match="...") as a context manager, or pytest.deprecated_call() for deprecation warnings. To ensure no warning is raised, use warnings.catch_warnings() + simplefilter("error").

28 What does pytest.approx do?

Compares floating-point numbers (and sequences/dicts) with tolerance, avoiding false negatives from binary floating-point.

assert 0.1 + 0.2 == pytest.approx(0.3)

Mocking & monkeypatch

29 Difference between monkeypatch and unittest.mock?

monkeypatch temporarily modifies environment, attributes, dicts, sys.path, and CWD — ideal for simple, reversible substitutions. unittest.mock (or pytest-mock) provides call tracking, return-value configuration, side effects, and assertion helpers. Use monkeypatch for env/attributes, mock for behavioural stubs.

30 How do you mock a function imported in another module?

Patch where it's used, not where it's defined:

# mymod.py has: from requests import get
# patch mymod.get, not requests.get
monkeypatch.setattr("mymod.get", fake_get)
31 What is mocker and how does pytest-mock help?

pytest-mock exposes a mocker fixture wrapping unittest.mock. It automatically undoes all patches at test end (no context manager needed) and gives you mocker.patch, mocker.spy, mocker.stub.

32 How would you test code that calls datetime.now()?

Freeze time. Either use freezegun / pytest-freezegun:

@pytest.mark.freeze_time("2020-01-01")
def test_new_year():
    assert datetime.now().year == 2020

Or inject a clock abstraction so the test passes a fake clock. Injection is preferable for long-lived code.

Advanced pytest

33 What is pytest_generate_tests and when do you need it?

A hook for dynamic parametrization — parameters defined at collection time from a data source (CSV, DB, environment). Use it when the values aren't known when the file is written.

34 How do you write a custom pytest plugin?

Create a module with hook functions (e.g. pytest_configure) and register it via entry point:

[project.entry-points.pytest11]
myplugin = "myplugin"

After pip install -e ., pytest loads it automatically. Verify with pytest --trace-config.

35 What is pytest_addoption and how do you use it?

Hook that registers custom CLI flags:

def pytest_addoption(parser):
    parser.addoption("--env", default="dev")

Read via request.config.getoption("--env").

36 What is pytest_collection_modifyitems?

A hook that lets you reorder, filter, or add markers to collected test items. Common use: auto-mark slow tests based on path, or reorder so unit tests run first.

37 What is pytest_assertrepr_compare?

A hook that lets you customize the failure message when two objects compare unequal. Useful for domain-specific types where the default diff isn't helpful.

38 What are sub-tests, and when do you use them instead of parametrize?

Sub-tests (with subtests.test(...)) let one test contain multiple independently-reported assertions. Use them when parameters aren't known at collection time (e.g., iterating over files in a directory) and you want to see all failures, not just the first. Use parametrize when values are known statically.

39 What is pytest.ExitCode and how do you use it?

Enum of pytest exit codes returned by pytest.main(). Use it in scripts instead of magic numbers:

if pytest.main(["tests/"]) == pytest.ExitCode.OK:
    ...
40 How do you run pytest programmatically? 
import pytest
exit_code = pytest.main(["-v", "tests/", "--maxfail=1"])

Useful for custom runners, IDEs, notebooks, dashboards.

Debugging & Running

41 How do you drop into a debugger on failure? 
pytest --pdb

Or use pytest.set_trace() at a point, run with -s so output isn't captured.

42 What does pytest --lf do?

Runs only the tests that failed last time (based on .pytest_cache). Great for iterating quickly on a broken test. --ff runs failures first, then the rest.

43 How do you find the slowest tests? 
pytest --durations=10
44 How do you see fixture setup order? 
pytest --setup-show
45 What does pytest --co do?

Collect-only. Lists which tests would run without executing them. Useful for debugging discovery problems.

46 How do you list all fixtures and markers registered? 
pytest --fixtures
pytest --markers
47 What is pytest --trace-config for?

Shows which plugins are loaded and their entry points. Invaluable when a plugin misbehaves or when you're not sure if your custom plugin registered.

Configuration & structure

48 Where can pytest configuration live?

In priority order: pytest.ini, pyproject.toml ([tool.pytest.ini_options] or [tool.pytest]), tox.ini, setup.cfg. Only one is used per invocation.

49 What is PYTEST_ADDOPTS?

An environment variable whose contents are appended to pytest's CLI arguments. Great for local defaults or CI overrides without touching config files.

PYTEST_ADDOPTS="-vv --pdb" pytest
50 Explain pytest import modes.
  • prepend (default): test's directory prepended to sys.path. Simple; can shadow same-named modules.
  • append: appended to sys.path. Rarely needed.
  • importlib: import by file path without touching sys.path. Requires __init__.py in test dirs to avoid name clashes.
51 When do you need __init__.py in your tests folder?
  • Same test module name in two folders: yes, or use --import-mode=importlib.
  • Shipping tests as a package: yes.
  • Traditional project with tests importing an installed package: no.

Plugins & quality

52 Name three pytest plugins you use and why.

Examples: pytest-cov (coverage), pytest-xdist (parallelism), pytest-mock (cleaner mocks), pytest-randomly (order independence), pytest-timeout (hang protection), pytest-asyncio (async tests).

53 How do you measure test coverage? 
pip install pytest-cov
pytest --cov=myapp --cov-report=term-missing --cov-report=html

In CI: --cov-report=xml + upload to Codecov/Coveralls.

54 What does pytest-randomly do and why use it?

Shuffles test order (and resets random seeds) each run. Exposes hidden test interdependence and order-dependent bugs before they hit CI.

55 How do you parallelize tests and what are the caveats?

pytest-xdist with pytest -n auto. Caveats: tests run in separate processes, so no shared in-memory state; session fixtures are per-worker; ports/files/DBs must be unique per worker (use workerinput["workerid"]). Output order is non-deterministic.

56 How do you mitigate flaky tests?
  • Detect with pytest-randomly.
  • Fix root causes (state, time, order, concurrency).
  • Use pytest-timeout to fail fast on hangs.
  • As a last resort: pytest-rerunfailures with @pytest.mark.flaky — but log and fix.
57 What is property-based testing and how does Hypothesis fit in?

Instead of specific inputs, you assert invariants ("for all x: add(x, 0) == x"). Hypothesis generates hundreds of inputs, then shrinks failures to the smallest reproducer. Integrates seamlessly with pytest via @given.

58 What is the difference between a mock and a fake?

A mock records calls and returns programmed values. A fake is a lightweight working implementation (in-memory DB, fake HTTP server). Fakes test more real behaviour; mocks are cheaper but more brittle.

59 How would you test a Django or FastAPI app with pytest?

Django: pytest-django with @pytest.mark.django_db. FastAPI: fastapi.testclient.TestClient plus httpx.AsyncClient for async, using fixtures to build the app. Both use conftest.py for shared fixtures.

60 How do you test async code?

Install pytest-asyncio, mark tests with @pytest.mark.asyncio (or set asyncio_mode = "auto"). Async fixtures are supported. Alternative: anyio's pytest plugin for asyncio + trio.

61 How do you test CLI tools?

Use subprocess.run with capsys isn't enough (it captures Python-level output only). Better: test the main() function directly by passing argv, capture stdout with capsys. Or use typer.testing.CliRunner / click.testing.CliRunner.

62 What is pytest.raises with ExceptionGroup (Python 3.11+)? 
with pytest.raises(ExceptionGroup) as exc:
    raise ExceptionGroup("many", [ValueError("a"), TypeError("b")])
assert len(exc.value.exceptions) == 2
63 How do you add a custom marker and prevent typos?

Register it in config and enable strict markers:

[pytest]
markers =
    smoke: quick smoke tests
addopts = --strict-markers

Unknown markers then raise errors instead of warnings.

64 What's the difference between pytest.ini and native [tool.pytest] in pyproject.toml?

[tool.pytest.ini_options] is INI compatibility mode (strings, quoted lists). Native [tool.pytest] (pytest 9+) uses proper TOML types (booleans, arrays, nested tables). Stick with ini_options for compatibility; adopt native TOML when you're on pytest 9+ and no longer need older versions.

65 What's a good folder layout for tests in a real project?
src/myapp/
├── __init__.py
└── calculator.py
tests/
├── conftest.py
├── test_calculator.py
├── unit/
│ └── test_math.py
└── integration/
    └── test_api.py

src/ layout prevents import shadowing, forces installation (via pip install -e .), and makes tests reflect the installed package.
